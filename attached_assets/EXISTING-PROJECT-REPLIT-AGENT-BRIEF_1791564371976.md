# Replit Agent brief — Legend Bucks training mode IN THE EXISTING PROJECT

Work in the currently open, existing Legend Bucks Replit project. Do NOT create a new Replit project, import the isolated-demo ZIP, replace the app, or deploy a separate site. The prior ZIP was for the wrong architecture. Inspect this project's current source, deployed revision, auth/roles, database configuration, sandbox code, approval/issuance flow, store gift-card lookup/spend flow, and test suite before editing. Report the proposed files and isolation boundary first.

Build an admin-controlled **Training Mode** within this same portal and deployment, reached from a clearly labelled Training entry point. It must use the actual existing manager, Accounting Admin, and Store workflows rather than a static mock-up. Use dummy accounts and dummy rewards/cards/receipts. Display a persistent, unmistakable `TRAINING — DUMMY DATA` banner on every training screen and transaction. Allow an authorized admin to reset/reseed only training records. Training staff must be able to practise manager reward actions, admin-only gift-card request approval and separate issuance, Accounting ledger/reconciliation, and store balance lookup, partial spend, repeat-submit rejection, and remaining-balance review. Preserve current production behaviour for real users.

**Hard isolation requirement:** the same project may serve both modes, but training data must be held in a physically or logically isolated training database/schema with separate training sessions/identities, not merely a `demo` column in the live ledger. All reads/writes, background jobs, cache keys, exports, storage, and audit events must be tenant-scoped server-side; do not trust a client-supplied training flag. A training request must never be able to read or mutate real employee balances, real cards, or production receipts, and a normal request must not expose training data. Block live email/SMS, gift-card vendors, Salesforce/accounting integrations, and production storage from training mode; use a visible simulated outbox. Full bearer card codes must never appear in URLs, logs, exports, or screenshots. Fail closed if isolation, seed, or training DB configuration is missing. Do not copy production people or transactions into the training store.

The existing source may have a `LEGEND_BUCKS_SANDBOX` development-only mechanism. Inspect it before reuse; do NOT flip it on in a production deployment or relax its guard simply to make this work. Design a production-safe, server-enforced training tenant within the current Replit project, or report a BLOCKER if this cannot be isolated safely with its hosting/database constraints. No `db push`, seed, destructive migration, or fixture tests against production. Back up and review any production migration separately before execution. Do not print secrets, credentials, full card codes, or real customer data in Agent output.

Verification before claiming ready: show the files changed and test results; use dummy sessions for each role and exercise both UI and API authorization. Demonstrate a dummy card issue, balance lookup, CAD partial spend with receipt reference, updated remaining balance, duplicate request rejection, and concurrent spend protection; verify manager cannot approve/issue cards, and training actions cannot affect live data or send real notifications. Run regression checks on normal portal workflows. Give the owner one in-project Training URL/path and a concise pass/blocker table. If deployment cannot be completed safely, leave production unchanged and state the specific blocker. Do not claim that training tests approve real store tender or Accounting treatment.
